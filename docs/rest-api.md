# REST API — I Was Here

Документация описывает HTTP-интерфейс сервиса `i-was-here`: единственную сущность «Пользователь» и пять операций над ней. Всё, что ниже, соответствует текущей реализации в `cmd/api` и `internal/*`.

> Коды ответов соответствуют реализации: отсутствующий пользователь — `404`, занятый логин — `409`, нарушения валидации и слишком длинный пароль — `400`. Нюансы, которые не видны из таблиц, собраны в разделе «Известные расхождения».

## 1. Общие сведения

| Параметр | Значение |
|---|---|
| Базовый URL | `http://localhost:8080` |
| Префикс версии | нет |
| Формат обмена | JSON, UTF-8 |
| `Content-Type` успешных ответов | `application/json` |
| `Content-Type` ошибок | `text/plain; charset=utf-8` |
| Аутентификация | отсутствует |
| Время чтения запроса (сервер) | 10 с |
| Время записи ответа (сервер) | 10 с |
| Keep-alive простаивает | 60 с |

Порт `8080` задан константой в `cmd/api/main.go`, переменной окружения для него нет.

Маршрутизация — стандартный `http.ServeMux` с шаблонами методов:

```
POST   /users
GET    /users
GET    /users/{id}
PATCH  /users/{id}
DELETE /users/{id}
```

Что из этого следует для клиента:

- **Слеш в конце — это другой путь.** `/users/` и `/users/4/` не совпадают ни с одним шаблоном и возвращают `404 Not Found`.
- **Неподдерживаемый метод** возвращает `405 Method Not Allowed` и заголовок `Allow` с перечнем допустимых методов. Например, `PATCH /users` без идентификатора → `405`, `Allow: GET, HEAD, POST`.
- **Неизвестный путь** → `404 Not Found`, тело `404 page not found`.
- `HEAD` работает там, где есть `GET`.
- Регистр пути и имён query-параметров важен: `/Users` и `?Limit=5` не распознаются.

## 2. Модель User

```json
{
  "id": 4,
  "version": 7,
  "login": "bebrowski",
  "created_at": "2026-11-22T17:44:19.651564+03:00"
}
```

| Поле | Тип | Описание |
|---|---|---|
| `id` | integer | Первичный ключ, выдаётся БД, только чтение. |
| `version` | integer | Начинается с `1`, увеличивается на `1` при каждом фактическом изменении. Управляется сервером: клиент его не передаёт. Внутри используется как защита от одновременной перезаписи (`UPDATE ... WHERE version = $n`). |
| `login` | string | Уникальный логин, 3–32 символа. |
| `created_at` | string | Момент создания в формате RFC 3339. В БД хранится `TIMESTAMPTZ`, в ответе отдаётся в часовом поясе сервера (например, `+03:00`). |

**Пароль никогда не возвращается.** Поле `Password` помечено `json:"-"` и не попадает ни в один ответ; в ответах на создание и изменение его также нет.

Схема в БД:

```sql
CREATE TABLE iwh.users (
    id         SERIAL      PRIMARY KEY,
    version    INTEGER     NOT NULL DEFAULT 1,
    login      VARCHAR(32) NOT NULL UNIQUE CHECK (char_length(login) BETWEEN 3 AND 32),
    password   VARCHAR(60) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL
);
```

`password` — хеш bcrypt длиной ровно 60 символов, а не открытый пароль.

## 3. Коды ответов

| Код | Когда |
|---|---|
| `200 OK` | Успешный `GET`, успешный `PATCH` (в том числе пустой патч). |
| `201 Created` | Успешный `POST /users`. |
| `204 No Content` | Успешный `DELETE` (тело отсутствует). |
| `400 Bad Request` | Тело не является корректным JSON; не прошла валидация полей; пароль длиннее 72 байт; `id` в пути не число или ≤ 0; `limit`/`cursor` не числа. |
| `404 Not Found` | Неизвестный путь; пользователя нет в `GET`, `PATCH` или `DELETE /users/{id}`. |
| `405 Method Not Allowed` | Метод не поддерживается для пути, в ответе есть `Allow`.
| `409 Conflict` | Логин уже занят другим пользователем при создании или переименовании. |
| `500 Internal Server Error` | Ошибка БД или внутренняя: недоступность БД, ошибка выполнения запроса, сбой хеширования. |

## 4. Ошибки

Все ошибки — не JSON, а короткая строка с переводом строки (`http.Error` добавляет `\n`):

```
HTTP/1.1 500 Internal Server Error
Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff

internal error
```

Полный перечень сообщений:

| Тело | Код | Причина |
|---|---|---|
| `invalid request body` | 400 | Тело пустое, не JSON или тип поля не совпадает (`"login": 5`). |
| `validate error` | 400 | Поля прочитаны, но нарушены ограничения длины или поля нет. |
| `invalid query params` | 400 | `limit` или `cursor` не целое число. |
| `invalid user id` | 400 | `{id}` в пути не целое число. |
| `negative or zero user id` | 400 | `{id}` ≤ 0. |
| `not found` | 404 | Пользователя с таким `id` нет. |
| `already exists` | 409 | Логин занят другим пользователем. |
| `invalid password` | 400 | Пароль длиннее 72 байт. |
| `internal error` | 500 | Ошибка БД или внутренняя ошибка сервера. |
| `404 page not found` | 404 | Такого маршрута нет. |
| `Method Not Allowed` | 405 | Метод не поддерживается. |

Тексты англоязычные и одинаковые для всех клиентов; машиночитаемого кода ошибки в теле нет.

## 5. Пагинация

`GET /users` использует **keyset-пагинацию по возрастанию `id`**, а не offset.

| Параметр | По умолчанию | Допустимый диапазон |
|---|---|---|
| `limit` | `20` | `0` или отрицательное → `20`; больше `50` → `50` |
| `cursor` | `0` | отрицательное → `0`; `0` означает «с начала» |

Правила:

- Пользователи отдаются всегда в порядке возрастания `id`.
- Выборка: `WHERE id > :cursor ORDER BY id ASC LIMIT :limit + 1`; лишняя строка нужна только чтобы понять, есть ли следующая страница.
- `next_cursor` — `id` **последнего элемента текущей страницы**, если после него есть ещё данные. Если страница последняя — `null`.
- Следующий запрос: `GET /users?limit=<limit>&cursor=<next_cursor>`.
- Пустая выборка — это `"users": []` (не `null`) и `"next_cursor": null`.
- Курсор — обычное целое число, а не подписанный токен. Если между запросами удалить пользователя, страницы могут «съехать» без дублей, но с пропуском удалённой записи — для отображения списка это ожидаемо.

Пример (id условные):

```
GET /users?limit=2&cursor=0
→ 200 {"users":[{"id":4,...},{"id":6,...}],"next_cursor":6}

GET /users?limit=2&cursor=6
→ 200 {"users":[{"id":7,...},{"id":8,...}],"next_cursor":null}
```

## 6. Эндпоинты

### 6.1. Создать пользователя

```
POST /users
```

**Тело:**

```json
{
  "login": "ivan",
  "password": "secret123"
}
```

**Ответ `201 Created`:**

```json
{
  "id": 11,
  "version": 1,
  "login": "ivan",
  "created_at": "2026-11-22T19:54:26.04998+03:00"
}
```

**Ошибки:**

| Ситуация | Код |
|---|---|
| Пустое или невалидное тело, неверный тип поля | 400 `invalid request body` |
| Логин короче 3 или длиннее 32 символов | 400 `validate error` |
| Пароль короче 8 или длиннее 64 символов | 400 `validate error` |
| Пароль длиннее 72 байт (например, 40 кириллических символов) | 400 `invalid password` |
| Логин уже существует | 409 `already exists` |

Особенности:

- Пароль хешируется bcrypt на сервере, в БД и в ответе его нет.
- `created_at` выставляет сервер в UTC, в ответ приходит в зоне сервера.
- Незнакомые поля JSON игнорируются, лишние данные после объекта тоже не проверяются: запрос `{...} garbage` будет принят.

**Пример:**

```bash
curl -i -X POST http://localhost:8080/users \
  -H 'Content-Type: application/json' \
  -d '{"login":"ivan","password":"secret123"}'
```

### 6.2. Список пользователей

```
GET /users?limit={limit}&cursor={cursor}
```

**Параметры query:** `limit` и `cursor` — необязательные целые числа, см. раздел 5.

**Ответ `200 OK`:**

```json
{
  "users": [
    {"id": 4, "version": 7, "login": "bebrowski", "created_at": "2026-11-22T17:44:19.651564+03:00"},
    {"id": 6, "version": 1, "login": "kukirmash4", "created_at": "2026-11-22T17:44:27.89268+03:00"}
  ],
  "next_cursor": null
}
```

Пароля в элементах нет. Если `cursor` указывает за пределы таблицы:

```json
{"users": [], "next_cursor": null}
```

**Ошибки:** `400 invalid query params`, если `limit` или `cursor` — не целое число (`?limit=abc`).

**Пример:**

```bash
curl 'http://localhost:8080/users?limit=2&cursor=0'
```

### 6.3. Получить пользователя

```
GET /users/{id}
```

**Ответ `200 OK`:** объект `User` (см. раздел 2).

**Ошибки:**

| Ситуация | Код |
|---|---|
| `{id}` не число | 400 `invalid user id` |
| `{id}` ≤ 0 | 400 `negative or zero user id` |
| Пользователя нет | 404 `not found` |

**Пример:**

```bash
curl http://localhost:8080/users/4
```

### 6.4. Изменить пользователя

```
PATCH /users/{id}
```

**Тело** — объект с любым подмножеством полей; оба поля необязательны:

```json
{"login": "ivan_new", "password": "newsecret123"}
```

Семантика:

- Отсутствующее поле не меняется. `{"login": "ivan_new"}` меняет только логин; хеш пароля при этом сохраняется.
- Пароль хешируется bcrypt заново; старый хеш заменяется.
- `version` увеличивается на `1` при каждом фактическом изменении.
- Пустой объект `{}` (или тело, где нет ни одного из двух полей) — **не ошибка и не запись**: возвращается `200` с текущим состоянием пользователя, `version` не меняется.
- Заголовков вида `If-Match`/`ETag` нет; клиент не может указать ожидаемую версию, поэтому конфликт версий разрешается только внутри, между одновременными запросами (`UPDATE ... WHERE version = $n`).

**Ответ `200 OK`** — обновлённый `User`:

```json
{
  "id": 11,
  "version": 4,
  "login": "ivan_new",
  "created_at": "2026-11-22T19:54:26.04998+03:00"
}
```

**Ошибки:**

| Ситуация | Код |
|---|---|
| Тело пустое / не JSON / неверный тип поля | 400 `invalid request body` |
| `login` короче 3 или длиннее 32 символов, пароль короче 8 / длиннее 64 | 400 `validate error` |
| `{id}` не число | 400 `invalid user id` |
| `{id}` ≤ 0 | 400 `negative or zero user id` |
| Пользователя нет | 404 `not found` |
| Новый логин занят другим пользователем | 409 `already exists` |
| Пароль длиннее 72 байт | 400 `invalid password` |

**Пример:**

```bash
curl -i -X PATCH http://localhost:8080/users/11 \
  -H 'Content-Type: application/json' \
  -d '{"login":"ivan_new"}'
```

### 6.5. Удалить пользователя

```
DELETE /users/{id}
```

**Ответ `204 No Content`** — без тела.

Удаление физическое: запись исчезает из таблицы, восстановления нет. Повторное удаление того же `id` пользователя уже не находит.

**Ошибки:**

| Ситуация | Код |
|---|---|
| `{id}` не число | 400 `invalid user id` |
| `{id}` ≤ 0 | 400 `negative or zero user id` |
| Пользователя нет (в том числе повторное удаление) | 404 `not found` |

**Пример:**

```bash
curl -i -X DELETE http://localhost:8080/users/11
```

## 7. Валидация

Ограничения проверяются в двух местах: в HTTP-слое (теги `validate` в `internal/handler/handler.go`) и в сервисе (`internal/service`). Нарушение в HTTP-слое даёт `400 validate error`, проверка длины пароля в сервисе — `400 invalid password`.

| Поле | Ограничение | Где проверяется |
|---|---|---|
| `login` | обязателен при создании; 3–32 символа (считаются руны) | handler + `CHECK` в БД |
| `login` | уникален | `UNIQUE` в БД → ошибка `23505` |
| `password` | обязателен при создании; 8–64 символа (руны) | handler |
| `password` | не длиннее 72 **байт** | `service.HashPassword` (ограничение bcrypt) |
| `id` в пути | целое, > 0 | handler |
| `limit`, `cursor` | целые числа | handler |

Важное следствие из двух последних строк: документация проекта говорит «8–64 символа», а фактически действует ещё и предел 72 байта. Для латиницы он не мешает, но 40 кириллических символов (80 байт) при длине 40 < 64 будут отклонены. Такое отклонение возвращает `400 invalid password`.

## 8. Ограничения реализации

Осознанные (и не очень) рамки текущей версии — клиенту о них нужно знать:

- **Нет аутентификации и авторизации.** Любой, кто достучался до порта, может прочитать, изменить и удалить любого пользователя. Эндпоинта входа в API фактически нет: `service.CheckPassword` написан, но ниоткуда не вызывается.
- **Нет проверки `Content-Type`.** Запрос с JSON-телом и `Content-Type: text/plain` будет обработан.
- **Нет ограничения размера тела запроса.** `http.MaxBytesReader` не используется, тело читается целиком.
- **Неизвестные поля игнорируются**, ошибки на опечатку в имени поля (`"logn"`) не будет — поле просто не изменится.
- **Нет ограничения частоты запросов** (rate limiting).
- **Нет `/health`** и других служебных эндпоинтов.
- **Ошибки — plain text, а не JSON**, и без машиночитаемого кода.
- **Пагинация только keyset**: нельзя запросить страницу номер N и нельзя узнать общее число пользователей.
- **Нет `ETag`/`If-Match`**: оптимистичная блокировка версий доступна только внутри сервера.
- **Нет сортировки и фильтров**: всегда `id ASC`, без поиска по логину.
- **Удаление физическое**, без мягкого удаления и без каскадов (связанных сущностей нет).

## 9. Известные расхождения

Расхождений с контрактом не осталось: отсутствие пользователя даёт `404`, занятый логин — `409`, слишком длинный пароль — `400`.

Что стоит держать в голове:

- Любая ошибка хеширования помечается как `invalid password`, включая редкие внутренние сбои `bcrypt`, а не только превышение 72 байт.
- Если запись удалили между `GetByID` и `UPDATE` (или не совпал `version` при одновременном изменении), `PATCH` вернёт `404 not found`, хотя в момент начала запроса пользователь ещё был.
- `GET /users` никогда не возвращает `404`: пустая страница — это `200` с `"users": []`.

## 10. Полный сценарий

```bash
BASE=http://localhost:8080

# 1. Создание
curl -s -X POST $BASE/users \
  -H 'Content-Type: application/json' \
  -d '{"login":"ivan","password":"secret123"}'
# {"id":11,"version":1,"login":"ivan","created_at":"2026-11-22T19:54:26.04998+03:00"}

# 2. Список, первая страница
curl -s "$BASE/users?limit=1&cursor=0"
# {"users":[{"id":4,...}],"next_cursor":4}

# 3. Следующая страница
curl -s "$BASE/users?limit=1&cursor=4"
# {"users":[{"id":6,...}],"next_cursor":6}

# 4. Чтение одного
curl -s $BASE/users/11

# 5. Смена логина (пароль сохраняется)
curl -s -X PATCH $BASE/users/11 -d '{"login":"ivan_new"}'
# {"id":11,"version":2,"login":"ivan_new",...}

# 6. Смена пароля
curl -s -X PATCH $BASE/users/11 -d '{"password":"newsecret123"}'
# {"id":11,"version":3,"login":"ivan_new",...}

# 7. Пустой патч — ничего не меняется, version на месте
curl -s -X PATCH $BASE/users/11 -d '{}'
# {"id":11,"version":3,...}

# 8. Удаление
curl -i -X DELETE $BASE/users/11
# HTTP/1.1 204 No Content

# 9. Повторное удаление — 404
curl -i -X DELETE $BASE/users/11
# HTTP/1.1 404 Not Found
```
